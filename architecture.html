Architecture & Methodology

How the Adaptive Multilevel Queue scheduler classifies work, scores priority, ages long-waiting tasks, and decides what runs next on every tick.

Queue classification & policies

QueueExample workloadsScheduling policyObjective
Emergency ECG alerts, ICU monitors, code-blue signals Preemptive Priority Immediate CPU access, lowest possible response time
Interactive Doctor dashboards, EMR lookups, nurse charting Round Robin (4-tick quantum) Fair, responsive time-sharing for clinician-facing UI
Background Billing batches, nightly backups, reports FCFS + promotion-based aging Best-effort throughput without blocking clinical work

Per-tick workflow

Every simulated tick runs through the same eight-step pipeline.

1

Arrival & classification

Each new process is tagged Emergency / Interactive / Background based on the clinical role of the application that spawned it.

2

Per-tick scan

The scheduler checks the Emergency queue first. If it's non-empty, the highest-priority emergency process is selected unconditionally.

3

Dynamic priority scoring

Within a queue, processes are scored by base priority, waiting time, and recent CPU usage — see the formula below.

4

Aging & promotion

A Background process that has waited past a configurable threshold is promoted into the Interactive queue, where it competes fairly via Round Robin instead of waiting for total CPU idleness.

5

Preemption check

If an Emergency task becomes ready while something else is running, that task is preempted immediately — no penalty — and placed back at the head of its own queue.

6

Dispatch & execution

The chosen process runs for one tick, or until its Round-Robin quantum (or a preemption) ends the slice.

7

Bookkeeping & requeue

Waiting time, turnaround time, and response time counters update; the process is requeued per its own policy.

8

Completion

When remaining burst time reaches zero, completion time is recorded and the process is removed from the run queue permanently.

Dynamic priority formula

Balances clinical urgency, fairness, and system efficiency.

effective_priority(p, now) =
  p.base_priority
  - aging_slope[p.queue] * (now - p.waiting_since)   // aging bonus
  + 0.1 * recent_cpu_usage(p)              // CPU-hog penalty

// Lower effective_priority => scheduled sooner
// aging_slope: Emergency = 0, Interactive = 0.5, Background = 0.2

Emergency's aging slope is intentionally zero — clinical severity, not wait time, governs ordering among emergencies. A background task that waits past 8 / aging_slope ticks is promoted into Interactive, which is what actually prevents starvation (the score alone only affects ordering within a queue).

Design rationale

Why preemptive priority for Emergency?

Clinical alerts have hard implicit deadlines — any queuing delay is a patient-safety risk, so Emergency work must interrupt anything else instantly.

Why Round Robin for Interactive?

Clinicians perceive responsiveness, not raw throughput, when using dashboards and EMR — short time slices keep the UI feeling live.

Why FCFS for Background?

These jobs are long and non-interactive; they only need to make forward progress without interfering with clinical flows.

Why is aging scoped to Background only?

So a flood of low-priority tasks can never accumulate enough "aged" priority to delay a genuine Emergency alert — patient safety always wins.
